- Every scope is decided in the spec before any lane starts.
- Lanes run in parallel, each an Opus lead with at most 2 Sonnet helpers.

## Lane rules (every brief)

1. **Read first**: this plan, your brief, the spec sections it names, and ARCHITECTURE.md's "Input is not action", "A key handler never blocks" and "How to add a modal".
2. **Your worktree only.** Never edit `C:\Code\bro` (another session may be working there), `release-060`, or another lane's worktree. Start with `git merge --ff-only origin/release/0.60`; when the main thread says a dependency merged, `git merge origin/release/0.60`.
3. **Team.** You are the Opus lead. At most 2 Sonnet helpers at once (Agent tool, `model: "sonnet"`, `general-purpose`, or `Explore` for read-only sweeps). Each helper gets a written contract: the goal, the files it may edit (disjoint from yours and from the other helper's), what done means, and "do not run cargo or npm builds or tests; do not commit". You run every build and test, one at a time. You review every helper diff before you commit it. Helpers never commit, push, merge or touch another worktree.
4. **Commits**: plain house-style sentences saying what changed and why. No trailers of any kind: no Co-Authored-By, no "Generated with". Commit at each green step.
5. **Not yours**: version numbers, `CHANGELOG.md`, `docs/releases/`, `learn.rs` WHATS_NEW, `docs/keys.md`. Put a CHANGELOG-ready paragraph (bold lead-in, plain sentences, what the user sees) and any key you bound in your PR body.
6. **Owned files only.** Your brief lists them. Protocol changes are the foundation's alone; use `STUDIO_PROTOCOL` and the types it landed. If a contract is wrong or missing, stop and say so in your PR draft rather than editing a shared file. The e2e harnesses (`crates/nebula/tests/e2e_windows/{harness,flows,main}.rs`, `desktop/e2e/{harness,webdriver,prepare,paths}.mjs`, `desktop/e2e/desktop.e2e.mjs`) belong to the main thread (the visual-qa brief alone grants a screenshot helper in `harness.mjs`): put any helper your flows need in your own e2e file. The fake agent (`e2e_windows/agent.rs`) is the ledger lane's; ask it, through the main thread, for a step you need.
7. **Isolation.** Never run a kete binary without `NEBULA_RUNTIME_DIR` and `NEBULA_DATA_DIR` set to fresh temp dirs (it migrates real user data). Never run `claude` for real (Jay's subscriptions; real usage windows); `claude --help` text only. Never install a real scheduled task. The Windows e2e harness isolates itself; its configs keep `show_tips: false` and `whats_new_seen: 999.0`.
8. **Machine.** `CARGO_BUILD_JOBS=3`, `CARGO_INCREMENTAL=0`. One cargo command at a time, per crate; never `cargo test --workspace`; no Docker in a lane (CI covers Linux on the PR); no benchmarks or CPU-saturating loads (a P-core on this PC is failing).
9. **Hard rule: no real OS input.** No SendInput, keybd_event, mouse_event, AutoHotkey, PowerShell SendKeys, focus stealing or Alt-taps. Jay uses this PC; real input once captured his typing. Drive the desktop only through WebDriver (desktop/e2e) and the TUI only through its test harness or the e2e PTY. Never overwrite the system clipboard outside the e2e harness's save and restore helpers.
10. **UI.** Every control has a visible affordance, a tooltip naming its key, keyboard access, Workshop styling (bone, soot, ember; square corners; 1px rules; no shadows; Geist), and works at 640 px (desktop) and 80x24 (TUI). Ember means needs you, only. Status never relies on colour alone. User-facing copy in Kete's voice: plain, short, no em dashes.
11. **Menus are critical.** Any menu row you add is state-aware (what shows, what is enabled). Your PR lists rows added, rows considered and rejected, and why.
12. **Gates before you push**: `cargo fmt --all`; `cargo clippy -p <each crate you touched> --all-targets -- -D warnings`; `cargo test -p <each crate you touched>`; your Windows e2e flows (`cargo test -p nebula --test e2e_windows -- <your flow prefix>`); desktop if touched: `cd desktop && npm run check && npm test`, `cd desktop/src-tauri && cargo clippy -- -D warnings`, and your desktop e2e file (`npm run e2e:prepare`, then `node --test --test-concurrency=1 e2e/<file>`). `cfg(unix)` code is not compiled on Windows: keep it small and name it in the PR; CI's Ubuntu and macOS jobs check it.
13. **Disk.** Before pushing, delete your worktree's `target\debug\incremental` and `desktop\src-tauri\target\debug\incremental` by those exact paths.
14. **PR body** (your report): what you built (file:line), tests added, gates run with their summary lines, what you left out and why, menu rows, docs pages, the CHANGELOG paragraph, and anything Jay must check by hand. No attribution footer.
15. **Stop condition: a green PR against `release/0.60`.**

### CHANGELOG entry (draft; lanes' paragraphs refine it)

```markdown
## 0.60.0

Kete can run a studio of agents: an inbox the orchestrator works through on its own, role cards, a board and a gauntlet view over your repo's own files, a triage strip, a usage ledger, and an orchestrator that renews itself from a handover note.

- **Accounts for scripts.** `kete profile list --json` prints every account with its 5-hour and weekly readings. `kete profile pick` names the account a scripted launch should take and why, and holds it for 10 minutes so the next pick spreads; `--dry-run` shows every candidate and holds nothing. A reserved account (`kete profile reserve <name>`, or Reserve for me in Accounts) stays the default for your own sessions and is never picked for the orchestrator's.
- **Studio inbox and autonomy.** `kete studio enable <repo>` points Kete at a folder of inbox notes. When the orchestrator has sat idle for 45 seconds and nobody has typed to it for 2 minutes, Kete hands it a short note naming the new and changed notes, highest priority first, and which accounts have room. Autonomy A0 to A3 says how far it may go: A0 holds every spawn, A1 (the default) plans without pushing, A2 delivers, A3 may tag releases. Only you can change it, from your own shell or the apps.
- **Role cards.** `.kete/roles.toml` names roles with a model, effort, tool set, prompt and permission profile. `kete spawn --role runner`, the orchestrator's `--role`, and the role field in both quick prompts apply one. A role's tool list is the session's whole tool set. `kete roles check` prints exactly what each role gets.
- **Unattended sessions.** A role marked `unattended` runs without prompts in its own worktree while governance paths, Kete's own settings and force-pushes stay denied, checked twice: by Claude's deny rules and by Kete's guard on every shell command. Each account accepts bypass mode once, by you: `kete roles accept-bypass <account>`.
- **Studio board and gauntlet view.** One page shows each department's queue, lead, runners, last verdict, what waits on you and what it cost today. The gauntlet view lists every verdict by kind with its evidence and opens your review app on it. Both read your repo's files and keep no copy.
- **Triage strip.** Type one line under the orchestrator and it becomes a filed inbox note, routed by your triage desk in one turn. `kete studio note` does the same from a shell.
- **Usage ledger.** Tokens, estimated cost, tool uses and turns per session per day. `kete usage --csv` exports them.
- **Orchestrator renewal.** `kete orchestrator renew --from <note>` starts a fresh orchestrator with your handover note as its first prompt once the current turn ends, moves the role to it and archives the old one.
- **Upgrade note.** The protocol moved from 65 to 66 (additive: older apps keep working without the new pages) and the database to migration 37. Run `kete kill` and reopen.
```
